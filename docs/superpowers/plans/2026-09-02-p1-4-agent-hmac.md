# P1-4 Agent HMAC Request Signing Implementation Plan

## Goal

Add enterprise-grade request signing for Agent trace ingestion while preserving a controlled compatibility path for credentials created before signing-secret support.

## Steps

1. Inspect existing Agent credentials, Trace ingestion, migration, configuration, deployment, and one-time credential UI boundaries.
2. Add failing tests for canonical request signing, AES-GCM protection, legacy compatibility, required-signature mode, body hashing, and handler metadata propagation.
3. Implement versioned AES-GCM signing-secret storage and migration v5; never serialize ciphertext or plaintext through Agent list APIs.
4. Generate and return API key plus signing secret once on Agent create/rotation; verify HMAC before nonce claim and persist only safe audit metadata.
5. Wire configuration, CORS, API startup, Docker/Kubernetes secrets, and the frontend one-time credential reveal.
6. Verify with full Go tests, `go vet`, frontend tests/build, MySQL 3307 + Redis 3509 integration, and Compose/Kubernetes manifest validation.

## Acceptance criteria

- The canonical string and `v1=<lowercase hex>` HMAC protocol are deterministic and bound to method, path, timestamp, nonce, and exact body bytes.
- Signing secrets are 32 random bytes, returned once, and stored only as AES-256-GCM ciphertext.
- Invalid signatures and unavailable key material do not consume a nonce; replay protection remains active after signature verification.
- Old credentials remain usable only in compatibility mode; required mode rejects them.
- Create/rotate responses and the frontend clearly expose both one-time credentials, while list/audit paths never expose secrets.
- Existing and real MySQL/Redis paths pass without regressions.
